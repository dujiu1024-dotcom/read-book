# 知行 V1 验证策略与验收清单

> 状态：测试方案草案。当前用于 ReadAny Fork 可行性验证和知行后续 MVP 验收，不代表相关能力已经通过测试。  
> 原则：源码审查、单元测试、构建成功、真机运行和真实书籍质量评测是不同证据，必须分别记录。

## 1. 验证分层

| 层级 | 验证对象 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| L0 源码审查 | 架构、依赖、关键代码路径 | 识别设计与改造风险 | 不能证明项目可运行 |
| L1 自动化测试 | 单元测试、集成测试 | 指定逻辑在测试条件下正确 | 不能证明 App 可构建或真机可用 |
| L2 工程构建 | Reader 构建、Expo 配置、Android/iOS 编译 | 工程可生成目标构建产物 | 不能证明安装后运行正常 |
| L3 真机基础验证 | 安装、启动、导航、基础交互 | 目标设备可运行主要页面 | 不能证明完整阅读和 RAG 质量 |
| L4 核心链路验证 | 导入书籍、打开对话、发送消息、引用定位 | 阅读对话主流程可用 | 不能证明长期使用质量 |
| L5 质量与可靠性 | 真实中文书籍、检索准确性、记忆、异常恢复 | 核心体验达到约定标准 | 不能替代持续线上监控 |

每次报告必须标记具体层级和证据链接，不得将 L0/L1/L2 结果描述为端到端通过。

## 3. 知行核心产品验收

### 3.1 一书一长期对话

- [ ] 同一用户多次打开同一本书，始终进入同一个 Thread。
- [ ] 退出 App、重新登录或更换设备后，仍能恢复同一个 Thread。
- [ ] 同一用户并发打开同一本书，不会创建多个 Thread。
- [ ] 不同用户打开同一本书，各自拥有独立 Thread。
- [ ] 按章节、日期、话题变化不会自动创建新 Thread。
- [ ] 移出书架不会删除历史 Thread 和 Message。

### 3.2 对话基本能力

- [ ] 用户消息先持久化，再开始模型生成。
- [ ] 流式输出顺序正确，支持停止生成。
- [ ] 连续发送多条消息不会串线或错序。
- [ ] 重新生成不会覆盖旧回答。
- [ ] 网络重试不会产生重复用户消息。
- [ ] 退出重进后，历史消息正文和顺序完整。
- [ ] 模型调用失败时，错误状态可见且历史记录可恢复。

### 3.3 原文检索与引用

- [ ] 回答优先检索当前书籍的相关原文。
- [ ] 引用指向具体书籍版本、章节和原文片段。
- [ ] 点击引用可定位到原文；定位失败时提供可读的引用文本。
- [ ] 检索不足时明确说明，不伪造引用。
- [ ] 原文引用、作者观点推演、AI 模拟回答有明确区分。
- [ ] 书籍更新后，旧回答仍能追溯到旧版本。

### 3.4 认知记忆与笔记

- [ ] 用户明确观点与 AI 推断分开存储。
- [ ] 作者观点不被记为用户观点。
- [ ] 记忆可追溯到原始消息和原文依据。
- [ ] 用户观点发生变化时保留演进，不覆盖旧记录。
- [ ] AI 自动笔记与用户主动编辑区分来源。
- [ ] 用户编辑后的笔记不会被后台自动覆盖。
- [ ] 记忆抽取失败不影响消息持久化。

### 3.5 权限与隐私

- [ ] 用户不能读取其他用户的 Thread、Message、Note、Memory。
- [ ] 管理员默认不能查看用户私人聊天和笔记。
- [ ] 客户端不能通过篡改 user_id 访问他人数据。
- [ ] 模型密钥不出现在移动端。
- [ ] 日志不输出完整私人聊天内容和密钥。

## 4. 真实书籍质量评测

不能只用“能回答”作为通过标准。准备至少三类中文书籍样本：

| 类型 | 重点检查 |
|---|---|
| 结构清晰的 EPUB | 章节识别、段落切片、引用定位 |
| 排版复杂的 PDF | 页码映射、双栏/脚注/图表、OCR 质量 |
| TXT 或结构较弱文本 | 章节边界、段落连续性、长文本检索 |

每本书建立一组人工标注问题：

- 直接事实题：答案是否与原文一致。
- 跨段综合题：是否召回多个必要段落。
- 概念解释题：是否区分作者原意和模型补充解释。
- 反对作者题：能否准确复述作者论点，再讨论用户的反驳。
- 无依据问题：是否承认书中没有足够依据。
- 定位题：引用能否回到对应原文。

记录指标：

- Recall@K：人工标注的必要证据是否进入 Top K。
- Citation Precision：引用内容是否真正支持回答。
- Citation Coverage：关键结论是否有对应依据。
- Groundedness：回答是否超出原文证据却没有标注为推演。
- Locator Accuracy：章节、页码、段落定位是否准确。
- Latency / Token Cost：检索、模型调用耗时和成本。

第一轮先建立人工基准集，不提前设置未经验证的绝对阈值；跑出基线后再冻结阈值。

## 5. 异常与恢复测试

- [ ] 用户发送消息后立即断网。
- [ ] 模型流式输出过程中断网或 App 被杀进程。
- [ ] 用户重复点击发送。
- [ ] 同一 Thread 在两台设备同时发送消息。
- [ ] 笔记离线编辑期间云端版本已更新。
- [ ] 书籍处理任务中途失败并重试。
- [ ] 向量模型版本升级后重建索引。
- [ ] 书籍新版本发布后旧引用仍可追溯。

## 6. 当前执行顺序

1. 完成 ReadAny 上游 CI：自动化测试、Reader 构建、Expo 配置、Android APK。
2. 安装 APK，完成真机基础验证。
3. 选择一本合法可用的中文 EPUB，跑通导入、打开书籍、对话、引用定位。
4. 再选择复杂 PDF，验证解析与页码定位。
5. 根据真实结果确定 ReadAny 保留范围、删减范围和云端改造范围。
6. 通过评审后，才进入知行业务代码开发。

## 8. 入口平台调整与验证策略修订（2026-11-13）

本节修订此前以 Android/iOS 为默认用户端的验证顺序。若与第 2、6 节的移动端专属步骤冲突，以本节为准。

### 8.1 当前平台策略

- Android/iOS 真机验证暂停，不再作为当前放行条件。
- React Native / Expo 仅作为 ReadAny 上游工程验证对象，不代表知行最终客户端选型。
- 微信小程序是优先验证的主入口候选；服务号暂定为辅助入口；Web/H5 保留为备用与调试入口。
- 尚未创建实际小程序或服务号，也未验证账号资质、平台审核、实际接口权限和真实运行表现。
- 后端领域模型和 API 必须平台无关；入口只负责 UI、登录凭证交换、网络传输、缓存和平台生命周期。

### 8.2 验证分层修订

| 层级 | 验证对象 | 当前策略 |
|---|---|---|
| L0 | 源码/架构审查 | 持续执行 |
| L1 | 单元、集成、契约测试 | 持续执行，优先覆盖云端领域规则 |
| L2 | 构建与部署验证 | ReadAny 构建作为上游证据；后续验证服务端和小程序工程构建 |
| L3 | 平台运行验证 | 暂缓；取得小程序账号和开发环境后再做 |
| L4 | 核心业务链路 | 优先通过 API 集成测试和模拟客户端完成，不依赖真机 |
| L5 | 真实书籍质量与可靠性 | 使用固定样本、自动化评测和人工标注执行 |

### 8.3 当前自动化验证重点

1. 用户身份隔离与外部平台身份映射。
2. 同一 user + book 并发获取唯一 Thread。
3. Message 先持久化、幂等追加、序号一致和最终状态恢复。
4. SSE、WebSocket、轮询传输适配器不改变消息领域语义。
5. 客户端断开、后台挂起、重连、重复/乱序事件不丢失正式消息。
6. Citation locator 与具体客户端阅读器路由解耦。
7. RAG 使用真实中文 EPUB/PDF/TXT 样本建立人工标注基准。
8. Memory 来源追溯、用户观点与 AI 观点隔离、观点演进。
9. 管理员默认无法访问私人 Thread、Message、Note 和 Memory。
10. 书籍处理任务幂等、阶段重试、产物不可变和云端从原始文件重建。

- Android/iOS 真机安装和启动。
- Android/iOS 原生模块完整性。
- ReadAny 页面在小程序运行环境直接复用。
- 未经验证地假定 SSE 在小程序可用。
- 未经实际账号核验就认定服务号具备某项消息权限。

### 8.5 当前放行条件

- [ ] 平台无关领域模型和 API 契约通过静态审查。
- [ ] 身份隔离、唯一 Thread、Message 幂等和断线恢复具备自动化测试方案及执行证据。
- [ ] 流式传输抽象有明确主方案、降级方案和恢复协议。
- [ ] Citation locator 支持 EPUB/PDF/TXT 格式差异，不依赖客户端路由。
- [ ] 真实中文书籍 RAG 评测集和人工评分标准建立。
- [ ] Memory/Note 来源追溯和隐私权限边界通过测试设计审查。
- [ ] 小程序主体资质、类目、域名备案和平台接口限制列出待核实清单。
- [ ] 关键风险、未执行项和剩余假设记录在验证报告中。
- [ ] 用户确认接受剩余风险后，才讨论是否进入业务开发。

## 9. 核心数据模型与 API 契约静态审查发现（2026-11-13）

审查对象：docs/core-data-model.md。性质：设计审查，不是实现或运行测试。

### 9.1 已有设计方向合理

- 内部 User ID 与 Thread/Message 归属由服务端控制。
- Thread 以 local_dataset_id + book_revision_id 唯一约束实现同一数据集、同一具体版本一条长期对话。
- Message 采用追加写、客户端幂等键和服务端 sequence。
- 用户消息先持久化，再启动 Agent。
- Citation 固定到 BookRevision，避免书籍更新破坏历史引用。
- Note/Memory 与原始消息分开保存，保留来源和观点演进。
- 管理员默认不能读取私人聊天和笔记。
- 模型密钥只保存在服务端。

### 9.2 必须补齐的契约缺口

| 缺口 | 当前草案情况 | 需要明确的内容 |
|---|---|---|
| 外部身份映射 | User 有 email/phone 登录标识，未定义平台身份表 | 增加 ExternalIdentity；provider + provider_subject 唯一；服务端验证平台登录凭证；定义绑定/解绑/合并/注销 |
| 消息并发顺序 | Message 有 sequence 唯一约束 | 定义 sequence 原子分配策略；同一 Thread 并发发送时的排序规则；是否允许多个 Agent generation 并行 |
| 生成任务实体 | Message 有 streaming/completed/failed 状态，但无独立 generation/job 契约 | 明确 generation_id、取消、超时、重试、worker 崩溃恢复和重复执行保护 |
| 流式事件恢复 | 草案提到 SSE 和按 message_id 查询最终状态 | 定义事件 ID/序号、心跳、断线恢复语义；明确首版是否只恢复最终结果，不回放 token |
| 停止生成 | 产品要求支持停止，API 表未定义 stop endpoint | 定义取消接口和取消状态；区分用户取消、模型超时、服务端失败 |
| 消息正文结构 | Message content 为正文字符串，另有 citations | 明确 Markdown、文本片段、引用卡片、错误状态和工具输出的序列化版本；避免客户端依赖模型私有格式 |
| Note/Memory 来源完整性 | source_message_ids、citation_ids 作为字段列出 | 明确外键/关联表、来源删除策略、跨书记忆的 book_id 为空时如何保留书籍来源 |
| 权限落地 | 有归属校验原则，RLS 仍待决 | 定义服务端角色、数据库连接池下的用户上下文隔离、管理员/运维审计和负向越权测试 |
| 书籍文件访问 | 有 BookRevision 和对象存储原则 | 定义短时授权 URL、文件分段读取、下载权限、缓存策略和版权撤回后的失效策略 |

### 9.3 建议增加的契约测试

1. 同一外部身份并发登录，最终映射到唯一内部 User。
2. 两个设备并发请求同一本书的 Thread，最终只返回同一 Thread ID。
3. 同一 idempotency_key 重复提交，用户消息只写入一次。
4. 不同 idempotency_key 并发发送时，sequence 唯一且顺序规则确定。
5. Agent Worker 在用户消息落库后崩溃，任务可恢复且不会重复生成两条正式回答。
6. 用户停止生成与模型自然结束同时发生时，状态转换确定且幂等。
7. 客户端断线后按 message_id 查询，最终内容、引用和状态完整。
8. 伪造 user_id、thread_id、note_id 或 citation_id 均无法越权访问。
9. 管理员账号无法通过管理端 API 或数据库只读角色读取用户私人消息与笔记。
10. 账号注销只删除账号身份，不删除本地数据或服务器加密备份；恢复凭证独立于账号，注销后仍可恢复。

### 9.4 评审结论

现有数据模型足以作为讨论草案，但尚不足以直接生成稳定 API 或数据库迁移。优先补齐 ExternalIdentity、Generation Job、Message 事件与恢复、取消接口和来源关联约束。以上属于设计验证工作，不应在当前阶段直接实现业务代码。


## 10. 小程序流式响应能力补充核实（2026-11-13）

前文将小程序 SSE 能力列为待核实事项。进一步核对微信小程序网络 API 文档后，结论修正如下：

- wx.request 支持 enableChunked 开启 HTTP 分块传输。
- RequestTask.onChunkReceived 可监听新到达的分块，回调数据为 ArrayBuffer。
- 因此小程序具备实现流式文本接收的基础能力，不应简单表述为“不支持 SSE”。
- 但这不等于原生提供浏览器 EventSource。客户端仍需自行处理增量 UTF-8 解码、SSE 帧边界、半包/粘包、心跳、结束标记和异常关闭。
- 服务端/反向代理/CDN 必须避免缓冲响应；要验证首包时间、分块间隔、空闲超时和断线后恢复。
- 小程序进入后台时网络请求可能被中断，因此生成任务必须在服务端独立运行并持久化，不能依赖客户端长连接维持任务。

当前判断：小程序流式 Agent 对话在技术上有实现路径，属于“有平台 API 支持、仍需实际环境验证”，不是已通过。首版应把“消息先落库、服务端独立生成、客户端断线后查询最终结果”作为正确性底线；token 级实时展示属于可替换的体验层。

资料：
- 腾讯云微信小程序网络请求文档：wx.request 分块响应与 onChunkReceived（https://intl.cloud.tencent.com/zh/document/product/1219/57750）

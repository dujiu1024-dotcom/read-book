# 决策记录

记录产品讨论中已经明确的原则与尚待验证的事项。新决策追加记录，不静默覆盖历史。

## 已确认

### D-001：产品核心原则
- 状态：已确认
- 决策：用户通过与 Agent 对话来读书；Agent 不管理阅读过程，只参与阅读和思考。
- 影响：不做进度管理、阅读计划、打卡、提醒、自动续读等驱动机制。

### D-002：用户端与管理端边界
- 状态：已确认
- 决策：用户端只有手机端；PC Web 仅供管理员使用。
- 用户端入口：书城、书架、对话、我的。

### D-003：一本书一个长期对话
- 状态：已确认
- 决策：一本书对应唯一长期对话，不因章节或主题变化自动新建会话；原始聊天记录长期保存。

### D-004：默认单 Agent
- 状态：已确认
- 决策：第一版只有一个默认阅读导师 Agent，能力根据对话意图自然切换。

### D-005：本地初加工 + 云端完整处理
- 状态：已确认
- 决策：本地可进行初步解析、清洗、元数据提取和可选预切片/预向量化；云端必须保留完整解析、OCR、校验、正式切片、向量化、索引构建与更新能力。
- 约束：本地处理结果不是云端最终结果；云端是正式数据的权威来源。

### D-013：项目当前使用定位与开源复用原则
- 状态：已确认
- 决策：知行当前主要供用户本人及身边朋友共同使用，SaaS 是多人共享使用的产品形态，不预设闭源商业化。
- 影响：开源许可证不再作为排除候选项目的硬门槛；优先评估直接复用、Fork 改造和模块化集成的可行性。仍需记录许可证及依赖义务，不能将非商用等同于没有许可证要求。

- 原因：ReadAny 具备 Expo 客户端、书籍聊天、原文定位、切片和混合检索，但数据层以本地 SQLite 为主；TextSage 具备阶段化 PDF 处理、章节页码对齐和恢复机制，但面向教材 PDF，依赖特定目录结构和 Qdrant 等组件。
- 约束：尚未完成本地安装、构建、端到端运行及真实书籍检索评测。不得将源码抽查结论视为已验证可运行。

- 路线调整：ReadAny 不再作为小程序客户端直接 Fork 起点，当前仅作为阅读引擎、数据结构和宿主无关代码参考；详见 D-019、D-020 与 [ReadAny 适配清单](readany-adaptation-matrix.md)。

### D-015：云端权威数据 + 本地 SQLite 缓存（已被 D-030 替代）
- 状态：已废止，历史决策保留
- 原决策：知行采用云端权威数据模式，手机 SQLite 仅用于缓存、离线查看、草稿和待同步操作。
- 变更：2026-11-13 用户明确改为本地优先、服务器加密备份；以 D-030 为准。

### D-016：本地书籍加工 + 云端自动验收返工
- 状态：已确认（方案原则）；具体验收阈值待测试
- 决策：建设本地书籍加工工具，完成初加工后可一键上传；云端创建独立版本并自动监测/验收。不合格时返回结构化问题报告，本地按失败阶段定向重做；合格后进入正式入库候选，版权审核后才上架。
- 关键约束：云端必须保留完整重新解析、OCR、切片、向量化和索引构建能力；每次加工版本不可变，保留原始文件与处理记录。
- 说明：本地加工工具优先面向管理员 PC 工作流，不要求普通手机用户安装。

### D-018：ReadAny 移动端 Fork 的适配边界（阶段性，数据存储部分已被 D-030 替代）
- 状态：部分历史建议保留；其中“本地 SQLite 改为缓存/草稿/待同步队列”的建议已废止，现以本地为主存储、服务器加密备份为准
- 决策建议：继续以 ReadAny Expo 移动端为 Fork 起点；优先保留阅读器、导航、消息列表、输入框、Markdown 和引用定位组件；将正式 Thread/Message、Agent、RAG、笔记和书籍处理迁移至云端 API。
- 必须改造：一书多 Thread 改为同一书籍版本唯一 Thread；客户端模型直连改为服务端模型调用；WebDAV/S3/LAN 整库同步改为 API 级服务调用。关于本地 SQLite 的角色，原建议已被 D-030 替代，不再要求改为缓存。
- 依据：固定 ReadAny commit `fce44689e1377df1ae99a35e8e71d5e8b3a639d1` 的 `BookChatScreen`、chat Store、thread/message 查询、Agent、上下文管线、记忆压缩、RAG 检索和移动端同步适配器源码。

- 约束：本决策不授权直接开始知行业务代码改造。早期“先完成 M0 真机验证”的要求已被 D-019、D-020 的平台路线调整替代；当前先完成小程序适配验证和平台无关 API 契约评审。


### D-019：用户端入口暂不锁定，优先验证微信小程序

- 状态：阶段性方向，待平台资质与实际能力验证
- 决策：暂停将 React Native / Expo、Android 和 iOS 作为知行最终用户端路线。微信小程序作为优先验证的主入口候选；服务号作为辅助触达/跳转入口候选；Web/H5 保留为备用和调试入口。
- 核心约束：知行领域模型、Thread/Message、Agent、RAG、Citation、Note、Memory 和书籍处理均由平台无关的云端服务负责。客户端只承担展示、输入、身份接入、平台网络适配和短期缓存。
- 原因：产品核心是用户与 Agent 围绕书籍持续对话，而不是特定原生设备能力；小程序可能降低用户安装和使用门槛，但必须先验证平台网络、阅读组件、账号资质和发布规则。
- 服务号边界：不把客服消息机制作为 Agent 长期对话主通道；优先用于关注、菜单、服务通知和跳转，具体权限需实际账号核验。
- 验证要求：优先完成平台无关 API、身份映射、唯一 Thread、Message 幂等/断线恢复、传输层适配、Citation 定位契约和真实书籍 RAG 质量验证。小程序 SSE/WebSocket、文件阅读和平台审核待取得实际账号后验证。
- 约束：不代表已决定采用原生小程序、跨端框架或 H5；不授权开始业务代码开发。ReadAny 上游 CI 和 Android APK 成功只证明其 Expo 工程构建能力，不能推断可直接迁移到小程序。
- 依据：2026-11-13 平台网络能力和客服消息规则初审，详见验证策略第 8 节及后续平台专项记录。


### D-020：ReadAny 不再作为知行小程序客户端的直接 Fork 起点

- 状态：阶段性复核结论，客户端方案待验证
- 决策：ReadAny 继续作为阅读引擎、数据结构、交互设计和部分 HTML/JavaScript 逻辑的参考项目；不再默认把其 Expo App 作为知行小程序客户端的直接 Fork 起点。
- 源码依据：固定 commit 的 ReaderScreen 使用 React Native WebView、Expo Asset/DocumentPicker；reader.template.html 通过 window.ReactNativeWebView.postMessage 与宿主通信；local-file-server.ts 使用原生 Lighttpd 或 react-native-tcp-socket 在本机提供书籍文件和 Range 请求；ExtractorWebView 依赖隐藏 WebView 和原生桥接。
- 影响：ReaderScreen、React Native WebView 桥接、本机文件服务器和 Expo 文件访问层不能直接迁移到小程序。Foliate/foliate-js 阅读引擎、与宿主无关的 HTML/CSS/JavaScript、EPUB CFI 和部分定位模型仍有研究复用价值。
- 后续：比较小程序原生页面 + 共享引擎、小程序 web-view + 受控 H5 阅读器、独立小程序阅读组件三条路径；以 EPUB 加载、目录、选区、引用回跳、长文性能和文件访问作为验证指标。
- 约束：当前不选定 A/B/C，不开始客户端开发。详细源码证据见 docs/readany-adaptation-matrix.md 第 13 节。


### D-021：Agent 主导的原文精读，而非阅读器或摘要产品

- 状态：已确认
- 决策：知行不做阅读器，不支持选中文字提问。Agent 按作者章节结构和论述逻辑，逐个语义完整单元提供原文；用户先自主阅读、理解、复述、提问或质疑，之后 Agent 再讲解、讨论和辩论。
- 约束：原文是阅读主体，AI 解释是辅助；不得上来就替用户总结和嚼碎原文。
- 阅读节奏：根据用户思考行为动态调整讨论深度。持续追问、提出独立观点或反驳时深入讨论；浅尝辄止、无继续讨论意愿时简要交流后推进，允许略读，不允许跳过主线内容。
- 交互：论述单元展示完成后等待用户发言；不主动推送问题或下一段原文。用户主动要求继续时，才展示下一主线单元。

### D-022：作者论述逻辑是阅读主线红线

- 状态：已确认
- 决策：主线阅读严格按照作者原书章节结构和论述逻辑推进，不因个性化推荐随意重排。
- 允许：用户可以要求重新展示已读原文，或因知识关联查看其他章节、后续内容；允许沿用户思维链进行适度讨论。
- 约束：查看其他位置内容不改变主线位置，不构成跳读；讨论后由 Agent 引导式回归当前主线。允许略读已经理解的内容，不允许跳过主线内容。

### D-023：一个书籍版本一个 Thread，阅读轮次累积而非重置

- 状态：已确认，版本边界由 D-033 补充
- 决策：同一用户对同一个具体 BookRevision 只有一个长期 Thread。阅读轮次作为同一 Thread 下的阅读记录；必须完成该版本整本书的主线阅读后，才能开启下一轮。
- 约束：二刷、三刷仍遵循作者逻辑；所有历史对话、笔记和认知记录保留。用户可以随时复习已读内容，复习不等于开启新一轮。
- 完成本轮后：由 Agent 判断主线内容已讨论完毕，再询问用户是否开启下一轮，不自动重置。

### D-024：书籍上架前建立全书通用知识库

- 状态：已确认
- 决策：每本书进入商城前，先完成全书结构拆分和知识整理，至少覆盖章节层级、核心要点、关键概念、论证逻辑、思想脉络和章节关系，并形成该书通用知识库。
- 共享边界：书籍知识库是同一书籍版本的公共基础资产，可供所有获得访问权的用户复用；用户个人对话、笔记、认知记忆严格独立。
- 约束：Agent 必须先具备全书整体概念，再引导用户精读；不能只依赖当前段落的临时检索。

### D-025：用户发散允许，作者主线必须守住

- 状态：已确认
- 决策：允许用户沿自己的思维链联系现实、提出关联问题并适度发散；Agent 负责自然总结关联并引导回归作者当前论述。
- 约束：作者主线是不可突破的红线，不以用户发散为由重排、跳过主线内容。

### D-026：自动上下文压缩与认知沉淀，原始数据完整保留

- 状态：已确认
- 决策：Agent 自动压缩模型调用所需上下文，并提炼用户有价值的输出形成读书笔记和认知记忆。
- 重要信号：用户持续讨论、反复追问、独立观点、认知冲突、现实联系和观点变化；讨论长短不是唯一判断标准。
- 约束：压缩不等于删除。原始消息、原文展示记录、笔记、认知演变和来源关联均长期保留；用户观点、作者观点和 AI 观点必须区分。
- 交互：不设置收藏动作，不要求用户手动标记重点；用户可编辑、删除笔记。旧认知不被新认知覆盖。

### D-027：管理员上传书籍，管理员决定精读价值

- 状态：已确认
- 决策：书籍唯一入库途径为管理员上传并发布；管理员上传的书默认均值得精读，不由 Agent 再做书籍价值筛选。
- 约束：用户不上传书籍，不通过用户提交需求形成入库流程。

### D-028：加入书架获得永久访问权，移出书架仅软删除

- 状态：已确认
- 决策：用户将书籍加入书架即获得永久访问权；商城下架不影响已获得的访问权。
- 决策：用户删除/移出书架采用软删除，不做普通业务数据物理删除；书籍、Thread、Message、Note、Memory 和历史引用继续保留，可恢复访问关系。
- 约束：商城商品状态、书籍版本状态和用户访问权益必须独立建模。

### D-029：取消收藏机制，笔记由 Agent 自动识别沉淀

- 状态：已确认
- 决策：产品不提供收藏按钮或手动收藏动作。Agent 根据用户表达的认知价值自动识别并沉淀笔记。
- 约束：讨论频率是信号但不是唯一标准；简短的重要观点也应识别。自动笔记保留来源，区分用户原话、AI 整理和 AI 解释；认知变化保留历史，不覆盖旧观点。


### D-030：用户个人数据本地优先，服务器仅加密备份
- 状态：已确认
- 决策：用户个人阅读数据以本地设备为主存储，服务器只保存加密备份，不作为个人数据在线主库。
- 数据范围：书架、Thread、Message、原文展示记录、阅读轮次、Note、Memory 和来源关系。
- 约束：本地写入优先；备份上传失败不影响本地数据；服务器不得持有可直接解密用户备份的明文密钥。
- 影响：替代 D-015 和此前架构/数据模型中“云端权威、本地缓存”的用户数据方案。公共书籍、BookRevision 和全书知识库仍由服务器管理。

### D-031：账号与数据分离
- 状态：已确认
- 决策：账号代表身份和认证关系，不是用户个人数据的唯一容器。切换账号不自动迁移、合并或同步数据；用户需要时通过独立备份下载流程恢复到本地。
- 约束：恢复凭证必须独立于账号密码；账号注销不得导致备份无法恢复。

### D-032：账号注销不删除用户数据
- 状态：已确认
- 决策：账号注销只删除账号身份、登录凭证和认证映射，不删除本地数据或服务器加密备份。
- 约束：账号注销与数据销毁是两个不同动作；不得在注销流程中级联删除用户数据。

### D-033：书架权益绑定具体书籍版本
- 状态：已确认
- 决策：用户加入书架时绑定具体 BookRevision。书籍升级形成独立版本/独立书目，用户需要单独加入；旧版本权益和历史数据不自动迁移到新版。
- 影响：ShelfEntry 与 Thread 均按具体 BookRevision 建立关系；同一作品不同版本可分别拥有 Thread。

### D-034：原文呈现后等待用户发言
- 状态：已确认
- 决策：Agent 展示一个语义完整的原文论述单元后等待用户发言，不主动推送问题、测验、提醒或下一段原文。
- 交互：用户主动表达后 Agent 再回应；用户主动要求继续时展示下一主线单元。

### D-035：不对用户理解程度打分或考试
- 状态：已确认
- 决策：Agent 不设置理解评分、考试或达标判断。Agent 的职责是启发、回应和讨论，不监督用户学习。

### D-036：阅读界面采用原文区 + 讨论区
- 状态：已确认
- 决策：原文在上方展示并可折叠，讨论在下方展示。原文与讨论属于同一思维过程，用户讨论时可随时查看原文。

### D-037：全书主线全部展示和讨论后本轮完成
- 状态：已确认
- 决策：一轮阅读必须走完作者原书所有主线章节和论述单元；复习和临时查看不改变主线位置。完成后可询问用户是否开启下一轮，不自动开启。

### D-038：认知记忆自动沉淀并保留演变
- 状态：已确认
- 决策：Agent 自动识别用户重要观点、问题、冲突和认知变化，不设置收藏动作。新旧认知通过补充、修正、冲突、推翻、延伸建立关系，不覆盖旧观点。
- 约束：Agent 不得仅凭措辞差异擅自认定用户已改变立场；所有记忆保留原始消息来源。

### D-039：管理员工作台负责公共书籍加工和验收
- 状态：已确认
- 决策：管理员工作台提供书籍上传、版本管理、全书知识库加工、质量检查、异常修正和发布能力。
- 约束：管理员默认不得查看用户私人 Thread、Message、Note 和 Memory。


### D-040：用户直接要求继续时先确认是否略读
- 状态：已确认
- 决策：用户在当前论述单元尚未讨论时直接要求“继续”，Agent 不立即推进，而是先简短确认用户是否希望略读当前单元。
- 约束：确认略读后才推进下一主线单元；用户选择继续讨论则留在当前单元。该确认只在用户直接要求继续、当前单元尚未得到讨论时触发，不变成常驻提示或主动催促。

### D-041：注销后恢复能力保留，但不主动前台宣传
- 状态：已确认
- 决策：用户可以凭独立恢复凭证，在新账号下恢复原有数据集，包括书架权益和历史阅读数据。
- 交互边界：不在常规前台设置显眼的“恢复旧账号数据”入口，也不主动向用户推销或提示该能力；当用户主动进入恢复场景时，提供必要的恢复流程。
- 约束：恢复凭证独立于账号密码；恢复过程必须明确告知数据范围并防止覆盖当前本地数据。

### D-042：每次打开应用时触发备份
- 状态：已确认
- 决策：每次应用启动/打开时触发一次备份检查与备份任务。存在待备份变更时执行备份；当前备份已覆盖最新数据时可快速完成检查，不重复上传相同数据。
- 约束：备份失败、离线或网络不可用不得阻断应用启动和本地阅读；记录待备份状态，并在后续可用时补做。备份始终以本地数据为准。

### D-043：第一版不做多设备同步，新设备提供恢复提醒
- 状态：已确认
- 决策：第一版不提供多设备实时同步。新设备首次打开且本地没有知行数据时，提示用户是否从已有备份恢复；用户可选择暂不恢复。
- 决策：设备已有本地数据时，按本地数据变化执行增量备份，不将其解释为跨设备增量同步。
- 约束：不得自动合并不同设备的数据集；恢复前保护当前本地数据，恢复完成后仍以本地数据为主存储。

### D-044：书籍不同版本在商城独立展示
- 状态：已确认
- 决策：同一作品的不同 BookRevision 在商城中作为独立版本/独立书目展示，分别加入书架、分别取得访问权益。
- 约束：新版不替换旧版；旧版权益、Thread、笔记、认知记忆和历史引用继续绑定旧版本。

### D-045：恢复凭证丢失后的数据恢复边界
- 状态：已确认
- 决策：恢复凭证丢失，且不存在其他有效恢复方式时，用户数据无法恢复。服务器不设置管理员解密后门。
- 说明：无法恢复不等于服务器物理删除备份；服务器仍按已确认的数据保留与访问控制规则处理备份。

### D-046：清除个人数据采用软删除，服务器原始数据保持不动
- 状态：已确认
- 决策：用户主动清除个人数据时，删除当前设备上的个人阅读数据；服务器端不物理删除、不改写、不销毁原始加密备份及其解密材料。
- 服务器处理：将该数据集标记为已清除/停用，软删除或失效化其用户关联索引和可用授权信息，阻断读取、检索、下载、恢复及业务使用。
- 约束：原始备份和其他数据保持原样；不得销毁密钥，不得通过普通业务流程重新关联或恢复授权。该动作与移出书架、账号注销相互独立。

### D-047：离线阅读范围
- 状态：已确认
- 决策：离线时可以查看本地已缓存的书籍原文、历史对话、读书笔记、认知记录及已有阅读信息。
- 联网边界：AI 对话、跨章节智能检索和获取尚未缓存的内容需要联网。
- 约束：离线产生的编辑先保存在本地，网络恢复后再执行备份；离线能力不得依赖服务器可用。

### D-048：同一设备切换账号时隔离本地数据集
- 状态：已确认
- 决策：不同账号的数据集严格隔离。切换账号不删除原有数据，也不自动将原数据上传、迁移或合并到新账号。
- 交互：用户只有在明确选择某个已有数据集后，才能继续访问该数据集；未选择时不得默认展示或使用其他账号的数据。
- 约束：账号身份与本地数据集关联关系必须显式管理，切换账号不能改变数据集内容或服务器备份状态。


### D-049：第一阶段采用 PC Web，窄屏模拟小程序阅读体验

- 状态：已确认
- 决策：第一阶段用户端先采用 PC 浏览器运行的 Web 应用，不开发微信小程序。
- 界面要求：主要阅读与对话界面采用接近小程序的窄屏、单列布局，在 PC 页面中居中呈现；具体 CSS 视口尺寸由设计稿和可用性测试确定，不把某个设备像素尺寸写死为业务规则。
- 交互要求：优先保证单列阅读、原文区与讨论区的连续体验；不依赖 PC 宽屏多栏才能完成核心任务。PC 键鼠可用，但不能让核心流程只能通过复杂桌面操作完成。
- 技术边界：第一阶段使用标准 Web 浏览器能力，不引入微信小程序 API、审核、业务域名或微信运行时限制。未来是否适配小程序另行评估。
- 数据边界：该决定只改变第一阶段入口和呈现方式，不改变用户个人数据本地优先、服务器仅保存加密备份、账号与数据集隔离等既有原则。
- 验证重点：优先评估浏览器 IndexedDB/OPFS 等本地持久化方案、文件访问、事务/崩溃恢复、加密备份与恢复、阅读器兼容性和流式对话。
- ReadAny：保留为阅读引擎、数据结构和宿主无关代码参考；不因本决策恢复 Expo 原生客户端 Fork 路线。

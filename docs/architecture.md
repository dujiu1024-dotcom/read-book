# 技术架构与关键设计

> 本文记录当前讨论形成的技术方向，选型仍需通过开源项目源码、许可证、部署和验证测试进一步确认。

## 1. 总体架构

采用模块化单体，不初期拆分微服务。

- 手机用户端：React Native + Expo。
- 管理端：React + Vite + TypeScript + Ant Design。
- 后端：Python + FastAPI。
- 数据库：PostgreSQL。
- 向量检索：pgvector。
- 缓存与后台任务：Redis + Worker。
- 文件：S3 兼容对象存储。
- 模型：通过 API 调用第三方模型，不在自有服务器部署大模型。
- 部署：Docker Compose。

初期不引入独立 Qdrant、Elasticsearch、Milvus、Neo4j、Kafka 等基础设施，除非实际压测或能力需求证明必要。

## 2. 本地初加工 + 云端完整处理

本地工具是可选的预处理客户端，不是独立的书籍生产系统。云端是书籍正式数据的权威来源。

### 本地可做的初加工
- 文件格式识别。
- 元数据初步提取。
- 文本初步解析和清洗。
- 章节结构初步识别。
- 可选的预切片、预向量化。
- 初步质量报告。

### 云端必须保留的完整能力
- 原始文件接收、存储和校验。
- 文件解析及必要时重新解析。
- OCR 与文本修复。
- 元数据、版本、章节和段落结构校正。
- 正式切片。
- Embedding 生成、索引构建和更新。
- 内容完整性与质量检查。
- 处理任务重试、增量更新和失败恢复。

本地结果是云端的可选输入材料，不是云端必须接受的最终结果。云端处理模式：
1. 直接复用：本地结果通过校验后复用。
2. 补充处理：只补足缺失或不完整环节。
3. 重新处理：本地结果不可信时，从原始文件重新处理。

## 3. 书籍数据与处理协议

本地与云端通过版本化的标准书籍包交换数据，避免依赖彼此内部数据库结构。

建议初始包结构：
```text
book-package/
├── manifest.json
├── source/                 # 原始文件（依据授权策略决定是否包含）
├── content/
│   ├── book.json
│   ├── chapters.json
│   └── chunks.jsonl
├── embeddings/             # 可选预向量
└── validation/
    └── report.json
```

每个切片至少包含：
- chunk_id
- chapter_id / chapter_title
- paragraph_index
- page_number（适用时）
- content
- 内容哈希
- 解析器与处理版本
- embedding_model / embedding_version（存在向量时）
- embedding_dimension

向量数据可采用紧凑二进制格式或独立数据文件，不要求全部以 JSON 浮点数组存储。

## 4. 向量与检索

- 本地可预生成向量，但云端必须能够独立生成和重建。
- 查询向量与书籍向量必须使用兼容的 Embedding 模型、版本、维度和预处理方式。
- 模型升级或维度变化时，支持重新构建索引。
- 云端保留原文切片；向量只用于检索，不能替代原文依据。
- 初期采用关键词 + 向量混合检索，检索结果需返回章节、段落和页码等定位信息。

## 5. 对话请求上下文

每轮不发送整本书和全部历史消息。按需组织：
- 最近若干轮对话（窗口大小通过效果与成本测试确定）。
- 当前问题相关原文及上下文。
- 相关历史讨论。
- 用户认知记忆。
- Agent 行为规范。

原始消息、原文、摘要、结构化记忆分别存储。摘要和记忆均可回溯原始消息。

## 6. 数据隔离与安全

- 用户私人聊天、观点、笔记必须按用户隔离。
- 公共书籍元数据可复用，私人内容不得跨用户访问。
- 管理员默认无权查看用户私人聊天和笔记。
- API Key 加密保存。
- 书籍文件、处理文本、聊天消息和结构化记忆按不同数据类型管理。
- 版权来源与授权信息随书籍版本记录。

## 7. 初期服务器建议

若文档解析、OCR 和向量化负载主要在后台 Worker，初期可从 4 核 8GB 服务器开始；开发测试可用 2 核 4GB。是否能降到更低配置，需通过真实并发、数据库和检索压测决定。无需 GPU（模型使用外部 API 时）。

本地预处理可以减少云端重复工作，但不能取消云端完整处理能力，也不能消除云端聊天、查询 Embedding、向量检索、数据库和模型 API 的成本。


## 8. 本地优先与云端权威数据的边界

知行不是 Local-first 产品，也不以手机作为业务数据权威端。它采用 Cloud-authoritative（云端权威）+ Local cache（本地缓存）的模式。

客户端职责：
- 展示书城、书架和长期对话。
- 缓存最近访问的书籍元数据、对话消息和读书笔记。
- 暂存未发送消息、离线草稿和必要的操作队列。
- 可选执行轻量本地检索或文件预处理，但不是必需条件。

云端职责：
- 保存用户、书架、书籍、Thread、Message、笔记和认知记忆的正式数据。
- 承担模型调用、对话上下文组织、原文检索、权限校验和跨设备同步。
- 负责书籍处理任务、验收、索引构建和正式版本发布。

客户端本地存储是性能和离线体验层，不是另一套独立主数据库。用户修改笔记时，可先写本地并标记待同步，再同步到云端；云端确认后更新同步状态。冲突处理需要保留用户编辑，不能由 AI 自动覆盖。

## 9. Thread 与 Message 数据模型

- Thread：长期对话容器。关联 user_id、book_id、created_at、updated_at、状态等。
- Message：对话中的单条消息，关联 thread_id，记录角色、正文、时间、生成状态、引用和必要的结构化内容。
- 业务约束：一个用户对一本书最多一个有效长期 Thread，数据库增加唯一约束 `(user_id, book_id)`。
- 打开书籍时，服务端获取该用户该书已有 Thread；不存在才创建。不得按章节、日期或话题自动创建新 Thread。
- 客户端可缓存 Thread 和 Message，但云端记录为正式历史；本地离线草稿在联网后提交。

## 10. 读书笔记的存储原则

读书笔记分为 AI 自动整理内容和用户主动编辑内容，两者均属于用户私人数据：
- 云端 PostgreSQL 保存正式笔记、版本、来源消息、书籍引用和用户修改记录。
- 客户端缓存近期笔记，支持快速打开和有限离线查看。
- 离线编辑先保存本地待同步版本；同步时按版本号/更新时间检测冲突，保留用户修改并提供冲突解决，不允许 AI 静默覆盖。
- 管理员默认不能读取用户笔记；书籍公共知识与用户私人笔记分表、分权限管理。

不建议第一版采用“笔记只存本地”。它会带来换机迁移、设备丢失、多设备访问、备份和对话来源关联问题，而当前产品没有明确的离线优先需求。

## 11. 本地书籍加工与云端验收闭环

本地加工工具建议面向管理员 PC 工作流，而不是要求每位手机用户安装处理环境。

流程：
1. 本地选择原始文件，完成元数据识别、格式解析、文本清洗、章节识别、切片和初步质量报告。
2. 生成带版本号的标准书籍包；记录源文件哈希、处理器版本、规则版本、切片定位和可选向量信息。
3. 一键上传，云端创建独立的 ingestion batch / book revision，不覆盖现有正式版本。
4. 云端后台自动验收；必要时从原始文件重新解析、OCR、清洗、切片和向量化。
5. 验收通过后进入正式入库候选状态；版权与元数据审核通过后才允许上架。
6. 验收不通过则返回结构化问题清单、失败阶段、问题定位和建议动作，本地工具据此只重做失败阶段并上传新版本。

云端验收至少包括：
- 文件完整性、格式和哈希校验。
- 元数据与版本匹配。
- 文本乱码、缺失、重复和段落顺序。
- 章节层级、页码映射和原文定位。
- Chunk 数量、长度分布、重叠和边界质量。
- 抽样切片回查原始文件，检查解析准确性。
- 向量模型、版本、维度和距离度量兼容性。
- 关键词/向量召回抽样测试。

上传与返工机制：
- 使用批次 ID、书籍版本 ID、幂等键和分片/断点续传。
- 每次处理产物不可变；新一轮返工生成新 revision。
- 每个阶段记录输入哈希、输出哈希、工具版本、耗时、状态和错误。
- 对通过的阶段允许按输入哈希复用缓存；输入或规则变化时重新执行。
- 验收结果区分通过、警告、失败；失败报告必须能定位到章节、页码或 chunk。
- 云端始终保留从原始文件独立重做的能力，不能信任本地报告作为唯一验收依据。



## 12. 客户端入口平台无关化（2026-11-13 阶段性修订）

此前文档中的“手机用户端 React Native + Expo”仅是候选技术方向，不再视为已确认选型。知行未来可能采用微信小程序、H5/Web 或原生 App；平台选择不应改变核心业务模型。

### 12.1 分层边界

- 展示入口：小程序、H5/Web、原生 App 均属于可替换客户端。
- 平台适配：登录凭证、分享、文件选择、网络连接、生命周期和本地缓存。
- 业务 API：统一认证上下文、书城、书架、Thread、Message、Note 等接口。
- 领域服务：唯一 Thread、消息持久化、Agent 编排、RAG、Citation、Memory、书籍处理。
- 基础设施：PostgreSQL、对象存储、任务队列、模型 API 等。

业务规则不得放在某个客户端实现。不同入口登录后必须映射到同一个内部 User，访问同一本书必须获取同一个长期 Thread。

### 12.2 对话传输层

消息领域模型与传输协议分离：

- 提交消息：HTTP API，先持久化用户消息并返回 message_id。
- 实时输出：SSE、WebSocket 或平台允许的其他机制均可作为传输适配器。
- 事件标识：每个流式事件包含 message_id 和单调递增 event_sequence。
- 最终状态：服务端持久化完整 Assistant Message 和生成状态。
- 恢复：客户端断线后按 message_id 查询状态/完整内容；如实现事件回放，按 event_sequence 补齐缺失事件。
- 幂等：客户端重复提交同一个 idempotency_key 不得创建重复消息。
- 生命周期：客户端进入后台、连接断开或页面销毁不得取消已被服务端接受的生成任务，除非用户明确发出取消请求。

第一版可先保证最终结果可恢复，不要求首版实现 token 级事件回放；但消息持久化和状态查询必须先于流式传输优化。

### 12.3 平台身份

新增外部身份映射概念：

- 内部 User ID 是知行唯一用户主键。
- ExternalIdentity 至少记录 provider、provider_subject、user_id、created_at、绑定状态。
- provider_subject 由平台登录流程在服务端验证后获得；不能信任客户端直接提交的 openid/unionid。
- 同一个平台身份只能绑定一个内部用户；同一个内部用户可以按产品规则绑定多个登录入口。
- 账号合并、解绑、注销、重新授权和主体切换需要审计记录。
- 平台 AppSecret、模型密钥和服务端凭证只保存在服务端。

具体字段、唯一约束和账号合并策略仍需在 core-data-model.md 中评审后冻结。

### 12.4 小程序运行约束

微信小程序网络 API 要求配置相应通信域名，HTTPS/WSS、域名备案和后台生命周期限制需纳入设计。小程序后台运行时网络连接可能被中断，因此不能依赖前端长连接作为生成任务的唯一执行载体。

阅读器组件也必须经过平台适配评估。EPUB CFI、PDF 页码/页内位置和 TXT 段落偏移属于内容定位协议；它们不应与某个客户端的页面路由、原生模块或 WebView 实现耦合。

### 12.5 当前架构决策

暂不决定原生小程序、跨端框架或 H5 容器。先验证平台无关的 API、身份、消息可靠性和阅读定位契约，再根据阅读器兼容性、交互体验、发布限制和维护成本选择入口。此修订不授权开始业务代码开发。


### 12.6 微信小程序流式响应补充

微信小程序 wx.request 提供 enableChunked 与 RequestTask.onChunkReceived，可接收服务端分块数据；onChunkReceived 返回 ArrayBuffer。它提供了实现 SSE 文本流的基础，但不是浏览器 EventSource 的直接等价物。

若选择小程序：
- 可优先验证 HTTP chunked + 自定义 SSE parser。
- 客户端需做增量 UTF-8 解码和事件帧缓冲，不能假设一个网络 chunk 对应一条完整 SSE event。
- 服务端与代理层需关闭不必要的响应缓冲，并设置合理心跳。
- 断线后仍以 message_id 查询服务端最终状态为准。
- WebSocket 和短轮询作为备选传输，不影响领域 API。

该能力有平台 API 文档依据，但尚未在知行真实小程序环境验证。详见验证策略第 10 节。


## 13. 知行精读 Agent、全书知识库与数据生命周期（2026-11-13）

### 13.1 上架前全书理解

每本书在进入商城前，先完成全书级加工，不允许仅在用户提问时临时理解局部段落。加工至少包括：
- 原书目录、章节、节和论述单元结构。
- 核心要点、关键概念、作者主张与论证链条。
- 论据、案例、重要引用及章节之间的思想关系。
- 原文切片、章节/段落定位和可追溯来源。
- 加工质量报告及管理员发布确认。

全书通用知识库与用户个人数据分离。相同 BookRevision 的通用知识库由多个用户共享；用户的 Thread、Message、Note、Memory 和阅读轮次按用户身份隔离。

### 13.2 Agent 精读调度

- Agent 必须掌握全书结构和作者论述逻辑，默认按作者原有顺序推进。
- 原文是主体：先提供语义完整的原文单元，用户阅读和表达理解后，再进行讲解、讨论或辩论。
- 讨论深度依据用户实际思考行为动态调整；有持续追问、独立观点和反驳时深入，浅尝辄止时简要交流后推进。
- 允许略读，不允许跳过主线节点。
- 用户可以复习已读原文，也可以要求展示其他章节或后续原文；此类展示不得改变主线位置。
- 用户可以沿自己的思维链适度发散，Agent 应引导式回归当前作者论述。
- 讨论充分后推荐下一单元并询问是否继续，不自动推送原文。

### 13.3 一书一主线与阅读轮次

- 数据库保证同一用户对同一本书唯一 Thread。
- 阅读轮次是 Thread 下的有序记录，不创建新 Thread。
- 只有上一轮完整走完全书主线后，才允许创建下一轮。
- 复习和临时查看其他章节不改变主线位置，不创建新轮次。
- 历史对话、原文展示记录、笔记和认知演变持续保留。

### 13.4 永久访问权与软删除

- 用户加入书架即获得永久访问权；商城下架不影响已获得的访问权。
- 用户移出书架仅软删除/隐藏 UserBook 关系，不级联删除 Thread、Message、Note、Memory、ReadingRound 或 Citation。
- 商城可见状态、书籍版本状态和用户访问权益独立管理。
- 书籍版本更新创建新 BookRevision；旧版本及历史引用保留，不能因新版本发布而使旧讨论失去依据。

### 13.5 长期数据保护

- 原始消息、笔记、认知记录和来源关系是长期资产。
- 上下文压缩只影响模型调用时的上下文组织，不删除原始数据。
- 必须具备定期备份、恢复演练、完整性校验和敏感操作审计。
- 管理员默认不能查看用户私人对话、笔记和认知记忆。

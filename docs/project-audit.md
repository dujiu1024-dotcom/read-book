## 1. 已经记录且不需要重复讨论的事项

- 产品核心：用户通过与 Agent 对话来读书，Agent 不管理阅读过程。
- 用户端手机、管理员端 PC Web。
- 一本书对应一个用户私有的长期对话。
- 用户个人数据以本地设备为主存储，服务器只保存加密备份。
- 公共书籍、BookRevision 和全书知识库由服务器管理；不得将公共书籍云端权威误解为用户私人数据云端权威。
- 本地 PC 书籍加工工具完成初加工后，一键上传；云端自动验收；失败返回结构化问题并支持定向返工。
- 云端保留完整解析、OCR、清洗、切片、向量化、索引构建和重建能力。
- ReadAny 作为移动端候选 Fork 起点；TextSage 作为处理流水线参考，尚待实际运行验证。

## 2. 术语澄清

### Thread 与 Message

- Thread 是一段长期对话的容器；知行中一个 user + 一本 book 对应一个 Thread。
- Message 是 Thread 内的一条用户或 Agent 消息。
- Thread 不是消息分支，也不是用户可见的多话题线程。
- 产品原则中“不做消息线程”应理解为不做消息分支、并行讨论串或复杂线程 UI；不影响内部使用 Thread 作为会话实体。

### 本地优先、边缘计算与数据权威边界

- ReadAny 的“本地优先”指业务数据和主要读写逻辑以设备本地 SQLite 为中心，网络服务不是唯一权威数据源；它不等于边缘计算。
- 边缘计算描述计算任务放在靠近数据产生端的设备或节点执行。管理员 PC 执行书籍预处理可视为本地/边缘处理的一种部署方式，但不是知行整体架构定位。
- ReadAny 的本地优先是设备本地数据主存储模式；知行现已确认采用用户个人数据本地优先、服务器加密备份。管理员 PC 书籍加工与云端验收是另一条独立链路。
- 手机缓存数据库与管理员 PC 处理工作目录是两个不同概念，不应混为一套 SQLite 数据库。

## 3. 已有方案仍需工程化的部分

### A. 本地书籍加工与云端验收

目前架构文档已写出流程，但以下内容尚未形成完整协议：

1. 标准书籍包的 JSON Schema、版本兼容和必填字段。
2. 原始文件、解析文本、章节、切片、定位信息、可选向量、质量报告之间的引用关系。
3. 云端验收状态机及状态迁移：上传中、待验收、验收中、通过、警告、失败、返工中、候选入库、已发布。
4. 每项质量规则的计算方法、抽样比例、阈值和严重级别。
5. 失败报告的机器可读格式：错误代码、阶段、文件/章节/页码/chunk 定位、证据、建议动作。
6. 本地工具如何读取失败报告，只重跑失败阶段及其下游依赖阶段。
7. 上传断点续传、幂等、重复提交、取消、超时和重试策略。
8. 通过验收后仍需版权/来源审核，不能自动直接公开上架。
9. 云端必须从原始文件独立重做；不能把本地报告或本地向量当作可信事实。

建议将本地工具设计为管理员 PC 工作台，提供“选择文件—预处理—查看报告—一键上传—查看云端验收—按报告返工—提交入库审核”的闭环。

### B. 用户笔记与本地数据（按新决策修订）

此前“笔记云端保存正式版本、本地只缓存”的方案已被 D-030 替代。

- Thread、Message、Note、Memory 和来源关系以本地数据库为主存储。
- 服务器只保存端到端加密备份，不维护可读明文主副本。
- 用户编辑先写本地；备份是显式/自动备份流程，不是实时云端同步。
- AI 自动整理内容与用户编辑内容必须区分来源和版本。
- 换账号不自动迁移；用户通过独立恢复凭证下载备份后恢复到本地。
- 账号注销只删除账号身份，不删除本地数据或服务器备份。

## 4. 产品规格中仍需补齐的内容

以下属于已有讨论中出现、但当前产品原则文档没有充分落成验收标准的要求：

1. 原文阅读体验：连续、完整展示必要原文上下文，不因检索切片造成跳章或碎片化体验；需要明确版权边界和展示交互。
2. 自适应讲解：复杂概念拆解、举例、追问并根据用户回答验证理解；简单内容也应确认用户是否理解，但不能机械考试化。
3. 独立思考：理解作者与认同作者分开评价；允许反驳作者，保留用户论据和未解决问题。
4. 作者对话：严格区分原文、基于理论的推演、AI 模拟回答。
5. 笔记质量：用户观点不能被 AI 改写成相反结论；每条笔记可追溯原始消息和书籍证据。
6. 书籍版本与质量：A/B/C 等级、版本匹配、缺页/乱码/章节错位等问题如何影响上架和 Agent 回答。

这些内容应转化为用户场景、Agent 规则和验收用例，而不只是散落在讨论记录中。

## 5. 技术决策仍待验证

- React Native + Expo 是否适合作为最终手机端工程底座。
- FastAPI、PostgreSQL + pgvector、Redis + Worker、对象存储的组合是否满足真实样本和并发。
- 中文/多语言 Embedding 模型及维度、成本和迁移策略。
- EPUB、PDF（文字型/扫描型/双栏/脚注/表格）、TXT 的解析质量。
- 混合检索、重排、邻近上下文扩展的实际效果。
- 多用户数据隔离、管理员默认不可读私人对话/笔记的权限测试。
- 模块化单体的部署、备份、恢复和升级方案。

## 6. 建议执行顺序

### P0：先验证开源底座
1. 固定并运行 ReadAny。
2. 固定并运行 TextSage。
3. 形成可运行证据、环境记录和复用改造清单。

### P1：冻结关键协议
1. 标准书籍包 Schema。
2. 本地处理流水线阶段定义与产物目录。
3. 云端验收规则、状态机和失败报告 Schema。
4. 定向返工规则与版本不可变策略。
5. Thread/Message/Note 的云端与本地数据同步协议。

### P2：补齐产品验收规格
1. 对话体验与自适应教学用例。
2. 原文连续性、引用定位和版权边界。
3. 记忆与笔记来源追溯、观点演进。
4. 书籍质量分级与上架门槛。

### P3：用户确认后再进入业务开发
P0/P1 的结果明确后，提交最终技术方案、工作量和开发计划；未经用户明确确认，不开始知行业务代码开发。

## 8. 平台入口与 ReadAny 复用路线调整（2026-11-13）

此前项目审查将 ReadAny 作为移动端 Fork 起点，并把 Android/iOS 运行验证列为主要 P0。用户已明确当前不要求真机验证，未来可能采用微信小程序或服务号。现阶段修订如下：

- Android/iOS 真机验证暂停，不作为当前放行条件。
- ReadAny 固定版本的 GitHub CI 已完成：Core/App 测试、Reader 构建、Expo 配置和 Android Debug APK 构建均成功；这仅证明上游 Expo 工程构建能力。
- ReadAny 的 ReaderScreen 依赖 React Native WebView、Expo 文件能力、本机 HTTP 文件服务器和 WebView 原生桥接，不适合作为小程序客户端直接 Fork。
- Foliate/foliate-js、部分 HTML/JS 阅读逻辑、EPUB CFI 和 Citation/Chunk 数据结构仍可继续研究复用。
- 微信小程序作为主入口候选，服务号作为辅助入口候选，Web/H5 保留为备用；账号资质、类目、实际接口权限、审核和真实运行能力未验证。
- 下一步优先验证平台无关的数据模型/API、外部身份映射、唯一 Thread、Message 幂等与恢复、传输层适配、Citation locator 和真实书籍 RAG 质量。

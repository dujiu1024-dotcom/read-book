## 3. 关键覆盖缺口

### 3.1 没有发现移动端端到端测试框架

在固定版本目录树中，没有发现 Detox、Maestro、Appium、Playwright 等移动端/端到端测试配置或测试目录。该判断基于仓库文件路径与命名审查；不排除外部手工测试流程，但当前仓库没有可重复执行的自动化 E2E 证据。

必须补做：
- APK 安装、首次启动、权限和原生模块加载。
- 书架进入书籍、阅读器加载、目录跳转和选区。
- 阅读器发起对话、流式响应、停止、重试。
- Citation 点击后回到正确原文位置。
- 强制结束 App 后重新打开，消息和书籍状态恢复。

### 3.2 Thread 与 Message 测试证明的是本地模型，不是知行目标模型

现有测试明确验证本地 SQLite 中：
- 一个 Book 可以查询到多条 Thread；
- 客户端可以插入、更新和删除 Thread；
- Message 直接写入本地数据库；
- 删除 Thread 时可以删除关联消息并写入 tombstone。

这些是 ReadAny 当前产品的既有行为。它们不能证明知行目标：
- 数据库层约束每个 user + book 只有一个 Thread；
- 两台设备并发获取时仍只创建一个 Thread；
- Message 云端追加写、幂等键和断线恢复；
- 移出书架不会误删 Thread/Message。

后续需要专门的服务端集成测试与并发测试，不能把现有 SQLite 测试当作通过证据。

### 3.3 RAG 单测不等于真实书籍问答

现有 RAG 单测包含 Mock 数据库和 Mock Embedding。它们能验证特定逻辑分支，但没有验证：
- 中文真实书籍的切片质量；
- 章节、页码、CFI 等定位的完整性；
- 混合检索的实际 Recall@K；
- Citation 是否支持回答中的关键结论；
- 书籍版本更新后历史引用是否仍指向原版本。

这些必须用固定版本的真实 EPUB/PDF 样本和人工标注问题集验证。

### 3.4 记忆测试覆盖范围有限

现有 `chat-memory.test.ts` 主要测试摘要压缩窗口，不覆盖知行需要的：
- 用户事实、理解、观点、假设和待解决问题的分类；
- 用户观点与 AI 观点来源隔离；
- 每条记忆回溯原始 Message 和书籍原文；
- 观点变化保留历史版本；
- 记忆抽取失败不影响消息保存。

### 3.5 构建测试与运行测试分离

当前 CI 通过的 Reader 构建和 Expo 配置验证，只能证明相关构建步骤可执行。Android APK 即使成功生成，也仍需设备安装和端到端操作验证。当前未获得 iOS 构建证据。

## 5. 后续验证计划（开发冻结期间）

按依赖顺序执行：

1. **完成当前 Android APK 构建**：获取 Artifact，确认包体、签名类型和保留期限。
2. **真机基础验证**：至少一台 Android 真机；记录设备型号、系统版本、安装/启动日志和截图。
3. **EPUB 核心链路**：使用合法可测试的中文 EPUB，验证导入、目录、翻页、选区和 Citation 回跳。
4. **对话稳定性**：连续对话、流式停止、异常重试、进程杀死后恢复、网络中断恢复。
5. **RAG 质量**：准备人工标注问题集，评测 Recall@K、Citation Precision、Citation Coverage、Groundedness、Locator Accuracy。
6. **PDF 链路**：使用含目录、页码、双栏/图表的真实 PDF，验证解析和定位；扫描 PDF 另设 OCR 样本。
7. **iOS 评估**：明确没有 macOS/Xcode 环境时的限制；有可用设备后补做 iOS development build 和基础验证。
8. **知行架构差异验证**：将本地多 Thread、客户端模型直连、本地 RAG、文件级同步列为明确的改造项，不以 ReadAny 原有测试通过替代知行目标验收。

## 6. 放行规则

在以下条件全部满足前，不批准进入知行业务开发：

- [ ] Android APK 成功生成并可下载。
- [ ] Android 真机安装、启动和原生模块检查通过。
- [ ] 中文 EPUB 阅读、对话、流式响应和引用回跳完整链路通过。
- [ ] 对话异常恢复和本地数据持久化验证通过。
- [ ] RAG 真实书籍质量有人工基准结果。
- [ ] 关键风险、上游缺陷和知行改造项有明确归属。
- [ ] 更新 P0 验证报告，并由产品侧确认是否接受剩余风险。

若某项因设备或外部服务不可用而阻塞，必须记录为“阻塞/未执行”，不能降级为“通过”。


## 7. 验证范围修订（2026-11-13）

用户确认当前不需要 Android/iOS 真机验证，未来入口可能采用微信小程序或服务号。因此第 5、6 节中“真机验证为放行条件”的表述已被本节修订：

- Android/iOS 真机安装、启动、原生模块检查不再是当前阶段的放行条件，暂缓执行。
- 第 4 次 CI 已完成：Core tests、Expo App tests、Reader build、Expo config 和 Android Debug APK 均成功。详见 P0 验证报告第 9 节。
- 上述 CI 只证明固定 ReadAny 上游 commit 的自动化测试与工程构建，不证明知行目标客户端或产品核心链路通过。
- ReadAny 是 Expo/React Native 工程，不能推断其页面和原生模块可直接迁移到微信小程序。

当前后续验证应转向平台无关核心：

1. 用户身份隔离和平台身份映射。
2. 同一用户同一本书的唯一 Thread，包含并发创建测试。
3. Message 幂等追加、持久化、事件序号和断线恢复。
4. SSE/WebSocket/轮询传输适配器的领域语义一致性。
5. Citation locator 与客户端阅读器路由解耦。
6. 真实中文 EPUB/PDF/TXT 的检索召回和引用准确性。
7. 认知记忆来源追溯、用户/AI观点隔离和观点演进。
8. 书籍处理流水线的幂等、重试、不可变产物和云端重建。

当前放行规则调整为：平台无关数据模型/API、身份权限、唯一 Thread、消息可靠性、引用定位、真实书籍质量和关键隐私边界均有明确测试方案及证据；小程序账号资质、接口权限、SSE/WebSocket、文件阅读和审核规则仍标记为待实际平台环境验证。所有未执行项必须保持“未执行/阻塞”，不能视为通过。

本次修订不授权开始知行业务代码开发。
